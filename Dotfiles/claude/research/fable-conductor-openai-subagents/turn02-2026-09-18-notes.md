# turn 2 — 2026-09-18 13:27:37 CDT

Question: can subswitch's forward leg (Claude Code -> Codex) be patched to keep subagent state durable, given that cache is sacrosanct for every model in the tree?

## Findings

- +SURE: the forward leg's ONLY state is one in-memory `Map<call_id, reasoning items[]>` (81 lines). Claude Code re-sends full history every request, so everything else is already a pure function of the request body. [A-subswitch-reasoning-cache-src-2026]
- +SURE: `prompt_cache_key` / `session_id` are a deterministic sha256 of (model + instructions + first user message) — already restart-stable. Side effect: two subagents spawned with byte-identical prompts share a key (author calls this benign under `store:false`). [A-subswitch-conversation-key-src-2026]
- +SURE: incoming `thinking` / `redacted_thinking` blocks are discarded by an explicit case arm, and reasoning items emit no Anthropic frames on the response side. No recorded rationale against carrying them client-side; the project's own research table lists "Preserve thinking/signatures, restart/resume" as unbuilt work. [A-subswitch-codex-request-src-2026]
- ~SUSPECT (reasoned, not measured): a reasoning-cache miss is a CACHE event, not just a quality event. OpenAI's prompt cache is prefix-matched on the translated input; reasoning items are part of that input. If item k was present in request N and absent in N+1 (restart, LRU eviction), the prefix diverges at k and everything after it is uncached for that request. It re-stabilises afterwards (the item stays gone), so cost is one cold request per conversation per loss event — but with a long-idle subagent being resumed after siblings churned the 4096-entry LRU, that loss event is likely.
- ~SUSPECT: reasoning that precedes a final text answer (no function_call in the response) is never stored (`reasoningItems.length > 0` is only checked on `function_call` done). Deterministically absent, so not a cache hazard; a minor continuity loss across `SendMessage` follow-ups.
- --WONDER (the one empirical unknown that decides the design): does Claude Code replay prior-turn `thinking` blocks + `signature` verbatim for a subagent, including after resume from its on-disk transcript? The Anthropic API requires verbatim replay inside a tool loop when thinking is on, so ~SUSPECT yes within a loop; across resume / older turns is -GUESS. No fixture in the subswitch repo captures a request containing a thinking block, so the repo offers no evidence either way.
- -GUESS: encrypted reasoning blobs have no documented short expiry, but OpenAI-side key rotation could invalidate old ones; any durable design must treat a rejected blob as a miss, not an error.

## Design options (for the fork)

1. Config-only: raise `providers.codex.reasoningCache.maxEntries` / `maxBytes`. Removes eviction; does nothing for restarts. Zero code.
2. Durable store: back `ReasoningCache` with `node:sqlite` (already within the project's Node >= 22.15 floor; no new dependency), write-through on `put`, read-through on `get` miss, TTL prune. ~80-120 lines. Proxy stays the state owner.
3. Stateless carry: emit each reasoning item to the client as a `thinking` block (summary text in `thinking`, serialized item in `signature`), decode on the way back, keep the LRU only as fallback. State then lives in Claude Code's own transcript — the same place subagent resume state already lives — so it survives proxy restart, CC restart, resume, and fork with no store, no TTL, no eviction. Depends on the --WONDER above.
3 subsumes 2 if the --WONDER resolves yes; 2 is the safe fallback if it resolves no.

## Strawman assessment: pi (or Codex) harness behind the Claude Code subagent

- The only interception point for a native Claude Code subagent is the Messages HTTP API. Putting a harness behind it means an API facade that runs a whole pi agent loop per request and returns text — structurally meridian's non-passthrough mode, inverted.
- That design must map "which pi session does this stateless HTTP request belong to" from request content. Claude Code subagents share the parent's session id, so the key would have to be a content fingerprint — the exact lineage-inference failure class that produced the user's meridian cache bust. [A-meridian-issue-820-2026]
- Translation-at-the-API (subswitch) has no lineage problem because it has no sessions. Recommendation: do not pursue the facade; if a native GPT harness is wanted, that is option D (codex-plugin-cc / app-server), not a native subagent.
