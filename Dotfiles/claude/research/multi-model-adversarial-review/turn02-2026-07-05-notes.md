## Findings
- finding-codex-exec-safe-default: `codex exec` runs in a **read-only sandbox by default**; escalation is explicit (`--sandbox workspace-write` / `danger-full-access`). Ships `--json` JSONL events, `-o` final-message file, `--output-schema` (JSON-Schema-conforming final answer), `--ephemeral`, and `codex exec resume --last/<id>` for threaded follow-ups. Requires a git repo by default. This makes bare `codex exec` a near-ideal safe dispatch primitive ([A-codex-noninteractive-2026]).
- finding-gemini-headless: Gemini CLI headless = non-TTY or `-p`; `--output-format json|stream-json` with usage stats and clean exit codes (0/1/42/53). Without `--yolo` it cannot run `run_shell_command` (registry error) but can still read files and report — read-only-ish by construction ([A-gemini-headless-doc-2026]; yolo caveat via [A-pal-clink-docs-2026]).
- finding-clink-defaults-hot: PAL `clink` shipped presets bypass safety: `gemini --yolo`, `codex exec --dangerously-bypass-approvals-and-sandbox`, `claude --permission-mode acceptEdits` — their own docs say CAUTION, confine to trusted workspaces, or edit `conf/cli_clients/*.json` to de-fang (which implies cloning/forking rather than uvx-from-git for anyone customizing) ([A-pal-clink-docs-2026]).
- finding-clink-mechanics: clink params = prompt / cli_name (gemini default, claude, codex, custom via conf/cli_clients/) / role (default, planner, codereviewer, custom via systemprompts/clink/) / files (passed as *references*, CLI reads them itself) / continuation_id. Conversation continuity across PAL tools and models is the genuine value-add over bare CLIs ([A-pal-clink-docs-2026]).
- finding-pal-license: PAL MCP is Apache-2.0 (LICENSE fetched raw) — FOSS requirement satisfied ([B-beehive-pal-mcp-2026]).
- finding-mu-mcp: μ-mcp = deliberate minimalist counter-design to zen/PAL: ONE chat tool over OpenRouter, MIT, persistent cross-session conversations, model registry + LLM-driven model selection, reasoning-effort passthrough, /mu:discuss multi-model discussion, /mu:challenge. Explicitly excludes workflows/step-tracking ("The best tool is the one that gets out of the way") — philosophically exactly the user's 'I own the process' stance, but API-shape only: the foreign model never gets an agentic harness ([B-mu-mcp-readme-2026]). Single-maintainer micro-project — fork-as-insurance if adopted.
- finding-windows-wrinkle: Codex CLI native Windows matured early 2026 (AppContainer sandbox, MS Store distribution) BUT a Jan-2026 issue reports `codex exec --sandbox read-only` on native Windows blocks even *reads*, breaking read-only automation there; WSL2 unaffected (snippet-grade lead, not registered). Plan: dispatch from WSL2/macOS; treat native-Windows dispatch as best-effort.
- finding-opencode-placement: OpenCode (anomalyco/opencode, MIT, ex-sst) = strong FOSS multi-provider agent CLI with `opencode run` headless + `opencode serve`; but subscription-auth for OpenAI/Google is doubtful (open issue asking for ChatGPT-sub login, Aug 2025; friction with vendor ToS --WONDER), and non-interactive permission handling has open bugs (issue #13851). As the *universal* runner it forfeits the free/subscription tiers that make the cheap stack cheap → niche extra, not backbone (snippets only, not registered).
- finding-delegator-placement: jarrodwatts/claude-delegator = plugin+MCP with opinionated 'expert' routing and synthesized responses — does the review *for* you; misfit for the user's own-process requirement (snippets only, not registered).
- finding-architecture: Every option reduces to glue around the vendor CLIs, because subscription/free-tier auth only flows through them (`codex` ↔ ChatGPT plan incl. Free; `gemini` ↔ Google-account 1000 req/day). The decision is glue thickness: none (Bash + dotfiles skill/agents), thin-MCP (mu-mcp for API-only models), thick-MCP (PAL clink for threading/orchestration).
